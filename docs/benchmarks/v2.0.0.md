# DeepVault Benchmark: Version 2.0.0 — Phase 2 Retrieval Engine Comparison

**Run ID:** `run_20260414_095030`  
**Run Date:** April 19, 2026  
**Judge Model:** `llama-3.3-70b-versatile` (faithfulness + relevance)  
**Embedding Model:** `BAAI/bge-small-en-v1.5` (384-dim)  
**Retrieval Top-K:** 5  
**Questions per strategy:** ~28–56 (balanced across 4 chunking strategies × 6 retrieval configs)  
**Dataset:** 60% enterprise synthetic documents, 40% academic research papers  

---

## 1. Executive Summary

This benchmark compares **6 retrieval configurations** across **4 chunking strategies** (fixed, sliding, structure, semantic), totalling 135 evaluated questions with LLM-as-judge scoring.

Phase 2 introduced three new retrieval capabilities built on top of the Phase 1 vector-only baseline:
- **BM25 Hybrid Retrieval (RRF)** — Merges dense vector search and BM25 keyword search via Reciprocal Rank Fusion.
- **Hybrid + Cross-Encoder Reranking** — Applies `ms-marco-MiniLM-L-6-v2` to re-score the top-20 RRF candidates.
- **Query Rewriting Variants** — An optional LLM-based query expansion step prepended to each retrieval pipeline.

**Key finding:** For the **Fixed chunking** strategy (the most consistent baseline), `hybrid` retrieval achieved the best faithfulness (3.30/5) and lowest hallucination rate (28.6%), outperforming vector-only across every quality metric.

## 3. Results by Retrieval Strategy

### 3.1 Fixed Window Chunking (n=48–56 per config)

The fixed window chunker (600 chars, 120 char overlap) is the most consistent baseline. Results for this strategy are the most statistically reliable.

| Retrieval | Faithfulness ↑ | Hallucination Rate ↓ | Hit Rate ↑ | CP@1 ↑ | P@K ↑ | Cost/1K ↓ | Efficiency ↑ |
|-----------|---------------|---------------------|-----------|--------|-------|-----------|-------------|
| `vector` | 3.196 | 37.5% | 92.9% | 71.4% | 55.4% | 5.82¢ | 0.549 |
| `vector_rewrite` | 3.033 | 46.7% | 93.3% | 63.3% | 45.7% | 5.79¢ | 0.524 |
| **`hybrid`** 🏆 | **3.304** | **28.6%** | 92.9% | 71.4% | 55.4% | 5.88¢ | **0.562** |
| `hybrid_rewrite` | 2.667 | 46.7% | 93.3% | 63.3% | 45.0% | 5.87¢ | 0.454 |
| `hybrid_rerank` | 3.018 | 41.1% | 92.9% | 71.4% | 53.3% | 5.86¢ | 0.515 |
| `hybrid_rerank_rewrite` | 3.188 | 35.4% | 95.8% | 64.6% | 38.2% | 6.24¢ | 0.511 |

> **Hybrid (no rewrite, no rerank) wins** for Fixed chunking. Adding query rewriting consistently degraded results — suggesting the fixed chunker's simple context worked best with direct queries.

### 3.4 Semantic Chunking (n=27–32 per config)

| Retrieval | Faithfulness ↑ | Hallucination Rate ↓ | Hit Rate ↑ | CP@1 ↑ | Cost/1K ↓ | Efficiency ↑ |
|-----------|---------------|---------------------|-----------|--------|-----------|-------------|
| `vector` | 3.000 | 46.9% | 93.8% | 68.8% | 5.94¢ | 0.505 |
| `vector_rewrite` | **3.345** | 41.4% | 96.6% | **79.3%** | 54.4¢ | 0.061 |
| `hybrid` | 3.323 | 41.9% | 96.8% | 83.9% | 39.0¢ | 0.085 |
| `hybrid_rewrite` | 3.207 | 44.8% | 96.6% | 75.9% | 62.3¢ | 0.052 |
| `hybrid_rerank` | 3.032 | 48.4% | 96.8% | 83.9% | 45.9¢ | 0.066 |
| `hybrid_rerank_rewrite` | 2.926 | 51.9% | 96.3% | 74.1% | 62.1¢ | 0.047 |

> ⚠️ **Cost anomaly detected:** Semantic chunking shows extreme cost-per-1K values (39–62¢ vs ~6¢ for others) in hybrid/rewrite configurations. This is caused by BM25 index initialization hitting the full semantic collection scroll on the first query, combined with semantic chunks being larger (fewer total chunks, more tokens per chunk). Faithfulness quality is high, but cost efficiency is severely degraded in hybrid mode.

> **Recommendation:** For semantic chunking, use `vector` retrieval. Hybrid retrieval's BM25 component struggles with semantic chunker's variable-size, topic-dense chunks.

## 5. Phase 1 vs Phase 2 Comparison (Vector Retrieval Baseline)

The V1 benchmark (April 2026 v2 post-refactor) used `llama-3.1-8b-instant` as judge. This benchmark uses `llama-3.3-70b-versatile`. The 70B judge scores more strictly, so absolute values are not directly comparable. Relative ranking within each run is valid.

| Chunker | V1 Faithfulness (8B judge) | V2 Vector Faithfulness (70B judge) | Change |
|---------|---------------------------|-------------------------------------|--------|
| Fixed | 3.22 | 3.196 | -0.8% (within margin) |
| Sliding | 3.34 | 2.714 | -18.9% (stricter judge) |
| Structure | 3.08 | 2.419 | -21.5% (stricter judge) |
| Semantic | 2.86 | 3.000 | +4.9% |

> The 70B judge applies tighter faithfulness standards, particularly penalizing speculative additions to answers. This is the expected and correct behaviour — `llama-3.3-70b` is a better judge. V2 benchmark numbers should be treated as the new ground truth.

## 6. Query Rewriting Analysis

Across all chunking strategies, query rewriting showed **inconsistent** results:

| Effect | Observed | Explanation |
|--------|----------|-------------|
| ✅ Positive for structure chunking | +29.5% faithfulness for `vector` → `vector_rewrite` | Rewriting expands heading-specific vocabulary |
| ⚠️ Neutral for fixed chunking | No consistent improvement | Fixed chunks are already vocabulary-rich |
| ❌ Degraded for sliding+rewrite | Hit rate dropped to 83.3% for `hybrid_rewrite` | Rewritten query sometimes drifts from original intent |

**Conclusion:** Query rewriting is not a universal improvement. It adds latency (~800ms per query for the rewrite LLM call) and increases cost. Future versions should implement **conditional rewriting** — only rewrite if the original query fails to retrieve sufficient results.

## 8. Key Findings and Recommendations

### Finding 1: Hybrid Retrieval Reduces Hallucination
For Fixed chunking, switching from `vector` to `hybrid` reduced the hallucination rate from **37.5% → 28.6%** (-8.9 percentage points). BM25 retrieves exact-match chunks that vector search misses when queries use specific terminology.

### Finding 2: Reranking Has Mixed Results
The cross-encoder reranker did not consistently improve faithfulness. It added ~100-200ms latency per query. This suggests that for this corpus size (~10K chunks), RRF fusion is already close to optimal ranking. Reranking is expected to show stronger gains with larger corpora (>100K chunks) where initial retrieval quality varies more.

### Finding 3: Query Rewriting Adds Latency With Uncertain Reward
Query rewriting adds an extra LLM call (~800ms). The quality improvement is chunking-strategy dependent. It is not recommended as a default setting.

### Finding 4: Semantic Chunker + Hybrid = Cost Trap
Hybrid retrieval with semantic chunks triggers expensive BM25 initialization and produces large chunks that generate high token counts. Use `vector` for semantic chunking only.

## 9. Recommended Production Configuration

Based on this benchmark, the recommended production configuration for DeepVault is:

| Setting | Value | Rationale |
|---------|-------|-----------|
| `CHUNKER_STRATEGY` | `fixed` | Most consistent across retrieval strategies. Lowest hallucination with hybrid. |
| `RETRIEVAL_STRATEGY` | `hybrid` | +3.4% faithfulness, -8.9pp hallucination vs vector-only. Minimal latency overhead. |
| Query rewriting | Disabled (default) | Uncertain quality gain, consistent latency cost. |
| Cross-encoder reranking | Optional (`hybrid_rerank`) | Use if latency budget allows and corpus grows above 50K chunks. |
